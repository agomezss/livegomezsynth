# T0.7 - Sequencer removal: dependency study (2026-11-14)

Question: can the step sequencer (D-50) be cut out of `src/firmware/src/obervave.c` cleanly?
Short answer: **not as a deletion**. It is the core of the monolith. A walking-skeleton replacement of the application glue is
cheaper and safer than carving.

## Findings (measured on `src/`, build 0.1-dev)

1. **Footprint.** The sequencer's pattern buffers are four 14,476 B objects in the pool: `pat`, `pat_old`, `pat_q`, `undo_pat`
   = **57.9 KB** (the pool is 328,368 of 344,064 B used). The big pool users are `fx_mem` 216 KB (effects delay/reverb memory) and
   `cv_px` 57.6 KB (the 240x240 canvas). In RAM (`.data+.bss`, 2.9 KB free) the sequencer-related objects are `psnd` 6 KB, `psect` 8 KB,
   `rec_open_part` 4 KB, `sector_load.buf` / `voice_copy_sector` 4 KB each. Code: `obervave.c` is one unity unit; its main routine
   `app_main` is 53.9 KB, `engine_audio` 15.6 KB, `rec_note_at` 1.3 KB, `draw_seq_knobs` 2.5 KB (the sequencer's share of flash
   is not separable from the unity build without removing it).
2. **Entanglement in `obervave.c` (3,316 lines):** `NTRK` x120, `seq_` x324, "step" x311, `pat` x137, `trk` x186, `rec` x55, ENDLESS x44.
   **The four sequencer tracks are the four parts** (`NTRK 4` and `NPART 4`; a track = a sound + mixer strip + pattern lane). Track
   sounds, mixer, scenes, keyboard config and pad banks all live in the pattern/scene structures. ENDLESS (arp recording,
   `obv_endless.h`, 83 refs) is built on `seqtrk_t` tracks. Other users: `obv_smk.h` (pads, 34 `seq_`), `obv_ui.h`, `obv_perf.h`,
   `smk_zoom_runtime.h`, `smk_sustain.h`, storage (`smk_store.h`: `BLOBS_AT`, `SLOTS_AT`, pattern slots, `NBLOB`).
3. **The voice/DSP module is only loosely coupled.** `obv_engine.h` (voices, arpeggiator, audio block, FX call) touches the
   sequencer through five hooks only: `seq_phase()`, `seq_starting()`, `seq_tick()`, `seq_q8_now()` and the note-source flag
   `seq_note_source` / `ctl_seq_transpose` (plus MIDI-out kind `MOUT_SEQ`). The arpeggiator takes its **tempo/transport from the
   sequencer clock** (`seq_phase`), so ARP needs a small clock of its own after the cut.
4. **Modules that look independent of the sequencer:** `obv_dsp.h`, `obv_params.h`, `obv_patches.h` (64 factory programs),
   `obv_fx.h`, `obv_drums.h`/`obv_drumx_core.h`/`obv_drum_kits.h`, `obv_multiengine.h`, `obv_supersaw.c`, `smk_midi_routes.h`,
   `smk_wheel.h`, `smk_sustain.h` (small hooks), `platform.c` (HAL glue). **Glue to be replaced:** `obervave.c` (pages, pad banks,
   mixer, split/layer, favorites, patterns, scenes, MIDI-MODE UI, zoom UI, backup/restore B1/B2).

## Options

|        | A. Carve the sequencer out of `obervave.c`                                                                                   | B. Replace the glue with a new lean app shell (recommended)                                                                                                                                                                                                                                                 |
| ------ | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Idea   | Delete steps/patterns/REC/ENDLESS/views one by one in the 3.3k-line file; fix what breaks                                    | New `lgs_main.c` that includes the reusable modules and implements only: boot, input mapping, audio ISR hook, display, USB MIDI/audio, ARP clock, storage (PATCH/PERFORM/EDIT/favorites). `obervave.c` leaves the build; pieces worth keeping (MIDI out, sustain, wheels, panel check) are ported on demand |
| Work   | Many small cuts through code we are going to replace anyway (the whole UI, pad banks, favorites, split/layer, mixer, scenes) | One new shell + five hooks stubbed; the new UI is written once                                                                                                                                                                                                                                              |
| Risk   | High: every cut can break USB, MIDI, drums, storage in non-obvious ways; no one owns the old behavior                        | Medium: new code, but small and tested; reuse is at module level                                                                                                                                                                                                                                            |
| Result | Same monolith minus features                                                                                                 | Smaller, ours; frees the 57.9 KB pool and the pattern flash                                                                                                                                                                                                                                                 |
| Tests  | Old tests are tied to the old behavior                                                                                       | Tests are written for the new shell; keep the module-level ones (flash map, wheel, drum pads, sustain, supersaw...)                                                                                                                                                                                         |

## Recommendation

Option B, as a **walking skeleton** (this is also the start of M1):

1. `lgs_app.c` (new application unit) that compiles with `platform.c`, `obv_dsp.h`, `obv_params.h`, `obv_fx.h`, `obv_engine.h`,
   `obv_patches.h`, `obv_drums*.h`, `obv_multiengine.h` and a stub `lgs_seq_stub.h` implementing the five hooks (no sequencer:
   `seq_phase` returns the ARP's own clock, `seq_starting` 0, `seq_tick` empty, `seq_q8_now` 0xFFFFFFFF).
2. Boot to a placeholder PATCH screen, keys play the SYN engine on part A, K8 = MASTER (D-03), the 64 factory programs browsable.
3. Verify audio + USB MIDI and the flash-safety rules in the host build and, later, the simulator (T0.6).
4. Port from `obervave.c` only what the specs keep (ARP/CHORD/GLOBAL pages, MIDI out, panel check, wheel/sustain, drums pads) as separate
   small units under `lgs/`, each with a test.
5. When the shell reaches feature parity with the specs, delete `obervave.c`, `obv_seq.h`, `obv_endless.h`, `obv_perf.h`,
   `smk_store.h` pattern parts, `smk_backup.h`, `smk_restore.h`, `smk_voice_store.h` pattern parts from `src/`.

Expected gain: pool -57.9 KB (patterns) plus whatever the unused UI/mixer/scene code frees; RAM `.data+.bss` relief from `psnd`,
`psect`, `rec_open_part` and the sector buffers; flash: the unity build shrinks with the dropped pages (measure after step 3).

## Result of T0.7a (walking skeleton, done)

`src/firmware/src/lgs_app.c` + `lgs_seq_stub.h` replace `obervave.c` as the application unit (default of `tools/lgs_build.py`; the old
monolith still builds with `LGS_APP_SRC=obervave.c`). It reuses `platform.c` (HAL glue, USB, OTA/recovery, boot guard), `obv_dsp.h`,
`obv_params.h`, `obv_fx.h`, `obv_engine.h`, `obv_patches.h`, `smk_midi_*`. Only two small additions were needed: a `b1_can_begin()` stub (the
SMKSYNTH bank-backup session never starts) and the five sequencer hooks.

|                  | obervave.c (SMKSYNTH 1.2.0) | lgs_app.c (skeleton) |
| ---------------- | --------------------------- | -------------------- |
| app image        | 224,880 B of 327,680        | **97,008 B**         |
| RAM `.data+.bss` | 95,392 of 98,304            | **42,336**           |
| pool             | 328,368 of 344,064          | **277,916**          |

The skeleton shows `[PATCH] n` + the program name, the keys play the SYN engine on part A with velocity, OCT-/OCT+ browse the 64 factory
programs. Checked on the host harness (`tests/run_host.sh`, fake FM-1): audio is produced (peak 5247) and the screen renders; the device
build passes every build check (RAM-text without calls into XIP, HAL-only register access). **Not yet run on hardware** (do not install: P-01).

The skeleton keeps all engine features of the old image that the specs need, and the remaining headroom is large: ~230 KB of flash
code, 56 KB of RAM and 66 KB of pool, which is enough for the engines of M2 (to be re-measured in T0.3).

## Consequences for the plan

- T0.7 becomes "walking skeleton + hooks" (sub-cards T0.7a-T0.7d in `tasks/M0-spike.md`) and absorbs part of T1.2 (mode state machine) and
  T0.4 (input mapping), because the shell owns input.
- ENDLESS (arp recording) and the SMKSYNTH MIDI MODE / Zoom / scope extras (D-47) are **dropped by default**; each can be ported later
  if wanted. Nothing in the specs depends on them.
- The old test list (24 control tests) is a mine of module tests but most include `obervave.c` and will not survive; keep the ones that
  test modules (flash map, wheel, drum pads, sustain, supersaw, MIDI routes).
- First-boot storage: with no patterns the user-data layout can be redesigned (T0.3): the app slot can grow because `0x57000..0x9CFFF`
  stops being a pattern bank.
